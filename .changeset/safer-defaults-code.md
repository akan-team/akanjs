`akan code` hardening:

- Every profile's deny list now also covers per-environment server env files (`env.server.{debug,develop,main,testing,local}*.ts`; the `env.server.ts` loader and the type file stay readable), Kubernetes and Jenkins credential files, `.akan/code/mcp.json` and `.akan/code/extensions/`, and the home credential stores `~/.akan`, `~/.ssh`, `~/.aws`, `~/.kube`, `~/.docker/config.json`, `~/.netrc` and `~/.git-credentials`, for read, write and the shell. A path is checked the way the engine reads it (`@`, `~`, `$HOME` and `file://` expand) and again through its real path, so a link cannot give a denied file another name. A profile passed to `CodeAgent.create` with its own `paths.deny` still decides its list.
- The `local` profile asks before a `web_fetch` to a host off a short list of documentation and registry hosts, and before a shell command that reaches the network (`curl`, `wget`, `ssh`, `scp`, `rsync`, `nc`, …); loopback is exempt. Where nobody can answer, such as a sub-agent or a one-shot run, the call is refused instead. `akan code --no-ask-network` turns the question off. A fetch the profile makes without asking follows a redirect only to a host it would also reach without asking. Other profiles are unchanged.
- `akan code` prints at start that the `local` profile is not a sandbox.
- A one-shot `akan code "<prompt>"` no longer offers approvals or questions, since nobody answers them during the run. `AKAN_CODE_CAN_PROMPT=1` restores them.
- MCP sign-in tokens in `~/.akan/code/mcpAuth.json` are bound to the server's origin instead of its name, so a server declared under a known name at another url gets no token. Tokens an older version stored by name move to the origin they were minted for; one whose origin cannot be read is dropped and signs in again.
- This repo's own `.akan/code/mcp.json` servers and `.akan/code/extensions/` start only after the user approves them once at a terminal. The approval is kept in `~/.akan/code/trust.json` (mode 0600) and asked again when that content changes. With nobody to ask they are not started, and the start notice says why. `akan code --trust-workspace` (`-T`) starts them for one run without asking. Servers in `~/.akan/code/mcp.json`, and ones `/mcp add` writes, need no approval.
- `akan code --rpc-listen tcp:…` asks each connection to open with `{"auth":"<token>"}` on its first line and answers `{"type":"reply","id":"auth","ok":true}`. The token is generated at start and written to `~/.akan/code/rpc/<port>.token` (mode 0600), or read from the file `AKAN_CODE_RPC_TOKEN_FILE` names. A connection whose first byte is not `{`, or that does not authenticate within five seconds, is closed, and it never displaces the client already attached. `--no-rpc-token` serves without a token. A non-loopback bind is refused unless `--rpc-bind-any` is given. A `unix:` socket is created with mode 0600 and asks for no token, though a client that sends one is answered.
- `AKAN_CODE_HOME`, `AKAN_CODE_CAN_PROMPT`, `AKAN_CODE_PROXY_*` and `AKAN_CODE_RPC_TOKEN_FILE` are ignored, with a start warning, when a dotenv file in the working directory names them, because Bun loads those files before the CLI runs. Export them in the shell instead; under `bun --no-env-file` they are always read. `~/.akan` and `~/.akan/code` are created with mode 0700, and an existing one the user owns with a looser mode is tightened.
