"akanjs": patch
---

A request that carries the app's session cookie more than once is now read as signed out: on the server, in SSR fetches, on websockets and in the browser, instead of taking whichever copy came first or last. An `Authorization: Bearer` header still wins. The API answers such a request with `Set-Cookie` headers that expire every copy written with a `Domain` attribute — for the request's host and up to four parent domains, at each of the first four directories of the request path, plain and partitioned — but never the app's own host-only cookie, and logs a warning with the cookie name, the count and the host, never a value. The host is the request's `Host` header, or `x-forwarded-host` when the request came through a trusted hop; an IP address, or a name longer than DNS allows, gets no sweep. In the browser `initAuth` expires them the same way and keeps the copy that remains; if two still remain, the page starts signed out. A library adds its own session cookies to the check with `SessionCookies.watch(name)` from `akanjs/common`; `libs/shared` adds its refresh-token cookies, and a refresh cookie sent twice is read as absent too.

A response that sweeps carries a few kilobytes of `Set-Cookie` headers, more for a deep path or a long host. If a proxy in front of the app limits response headers (ingress-nginx's `proxy-buffer-size` defaults to 4k), raise the limit to 16k, or that response fails with 502 and the visitor stays signed out.

Behaviour that changes for apps:

- Outside local the session cookie is now `__Host-jwt:<appName>`. A browser accepts that name only from the app's own host over HTTPS at `Path=/`, so neither a sibling subdomain nor a parent domain can plant a copy, and the sweep above never names it. A local server keeps `jwt:<appName>`, because plain http cannot keep the `Secure` the prefix needs. Every web visitor signs in once more after the upgrade. `initAuth`, sign-in and sign-out delete the older `jwt:<appName>` and the bare `jwt`, and neither is read. The token a native app keeps in secure storage stays under `jwt:<appName>`, so native users stay signed in. Code that reads the cookie by a hard-coded name should call `authTokenKey()` instead.
- The bare `jwt` cookie, which `jwt:<appName>` replaced in 3.0.0, is no longer read.
- `getStoredAuthToken` from `akanjs/client` no longer reads the bare `jwt` secret-storage key. A native install that holds only that key signs in once more.
- `initAuth` no longer takes a token from a `?jwt=` query parameter, and no longer writes back a cookie it only read. `setAuth` still writes it.
- `cookies()` from `akanjs/fetch` and `getCookie` / `cookies()` from `akanjs/client` read a name sent more than once as unset, percent-decode values, and no longer unwrap `j:` JSON values. The new `cookieJar()` in both returns every occurrence, with `read(name)`, `all(name)` and `readJson(name)`.
- `removeCookie` from `akanjs/client` writes `Secure` when it deletes a `__Host-` or `__Secure-` cookie.
- The `routes` domains and sub-route hosts a build records are declared to `AppHosts` at boot whatever the web setting, so a replica started with `AKAN_SSR=false` accepts them too. A build with `web: false` records none: list its hosts in `AKAN_ALLOWED_HOSTS` or pass them to `AppHosts.declare(hosts)`.
- Deprecated: `parseCookieHeader`, `readAuthToken` (use `readSessionToken(CookieJar.parse(header))`), `cookieHeaderHasAuthToken`, and `AppWsData.cookies` (use `jar`).

In `libs/shared`, SSO no longer builds the provider's `redirect_uri` from the `ssoOrigin` cookie the sign-in page set. The server takes the origin from the request; `x-forwarded-host` and `x-forwarded-proto` count only when the request came through a trusted hop — the gateway, or a proxy the trusted-proxy list admits (`AKAN_TRUSTED_PROXIES`). If TLS ends at a proxy outside that list, the origin is read with the scheme the app itself was reached on. Outside local the server refuses any host that is not the app's own with `shared.error.invalidSsoOrigin`. The app's own hosts are the `routes` domains in `akan.config.ts`, `AKAN_SUB_ROUTE_HOSTS`, `<app>-<environment>.<serveDomain>`, the `hostname` option or `HOST_NAME`, `AKAN_ALLOWED_HOSTS` (which, once set, also refuses every host it leaves out), and whatever server code passes to `AppHosts.declare(hosts)` from `akanjs/common`. If users sign in on another host, declare it in one of these before upgrading. The native SSO start uses the same origin and the same check.

Outside local the web sign-in's state cookie is now `__Host-ssoState`, the sign-up token cookie `__Host-signupToken`, and the refresh cookies `__Host-userRefreshToken:<appName>` and `__Host-adminRefreshToken:<appName>`, so a sign-in or a sign-up left unfinished across the upgrade has to be started again, and a web session cannot be refreshed past it. The earlier `<name>:<appName>` refresh cookies and the unscoped `userRefreshToken` and `adminRefreshToken` are no longer read; sign-in and sign-out delete them. `getSsoOrigin`, `NativeSso.publicOrigin` and `shared.error.invalidSsoCallbackMissingOrigin` are removed, and `readRefreshTokenCookie` now takes the request.
