The CLI's MCP tools, tunnels, env download, local registry and generated Dockerfile now stay narrower by default. Each changed default below names how to get the old behaviour back.

- **Workflow and repair commands run without a shell.** A command taken from a plan file, a run report or an MCP argument now runs as `bun run akan <args>`. It runs only when it is an `akan` subcommand whose arguments are plain words or flags; anything else is not run and fails with exit code 2. `akan workflow validate` and `apply` (and the `apply_workflow` / `run_validation` MCP tools) rebuild the validation commands from the workflow's own spec instead of reading them from the file.
- **Workflow inputs are plain names.** An `app`, `module`, `scalar`, `field`, `slice`, `mutation` or `interaction` input may hold letters, digits, `-` and `_`, with no dots, slashes or spaces. Planning reports anything else as `workflow-input-invalid`, and `apply` refuses such a plan with `workflow-plan-inputs-invalid`. The `app` must be one of the workspace's apps or libraries (`workflow-target-missing`), and the `repair_*` tools check their target the same way (`repair-input-unknown`).
- **MCP workflow files stay in `.akan/workflows/`.** `plan_workflow`'s `out`, `apply_workflow`'s `planPath` and the `runIdOrPlan` of `run_validation` and `doctor_workspace` must resolve inside the workspace's `.akan/workflows/` folder. A path elsewhere, or a link that leads out of it, is refused. A bare run id still means `.akan/workflows/runs/<id>.json`.
- **The cluster database tunnel listens on loopback.** The Redis or Postgres tunnel `akan start` opens to a cluster environment now listens on `127.0.0.1` instead of every interface. Set `SSH_TUNNEL_BIND_HOST=0.0.0.0` to listen on every interface again; the tunnel then logs a warning on each start.
- **The tunnel checks the SSH host key.** When `SSH_TUNNEL_HOST_FINGERPRINT` lists `SHA256:` fingerprints (comma-separated), only those keys are accepted. Otherwise the first key a host shows is kept in `~/.akan/ssh_known_hosts.json`, written with mode 0600, and a different key from that host is refused. The refusal names the host and the file entry to remove after a rebuild. `SSH_TUNNEL_KNOWN_HOSTS` points at another file, and `SSH_TUNNEL_HOST_FINGERPRINT=*` accepts any key, as before.
- **The tunnel signs in with a key when given one.** `SSH_TUNNEL_PRIVATE_KEY_PATH` (with `SSH_TUNNEL_PASSPHRASE` if the key has one) or `SSH_TUNNEL_PASSWORD` sets how the tunnel signs in. Without either, it still signs in with the workspace's repo name, as before, and logs a warning.
- **A repository's dotenv file cannot loosen the tunnel or pick the registry.** `SSH_TUNNEL_HOST_FINGERPRINT`, `SSH_TUNNEL_KNOWN_HOSTS`, `SSH_TUNNEL_BIND_HOST`, `SSH_TUNNEL_PRIVATE_KEY_PATH`, `SSH_TUNNEL_PASSPHRASE` and `AKAN_NPM_REGISTRY` are ignored, with a warning, when a dotenv file in the working directory names them, since Bun loads those files before the CLI runs; `create-akan-workspace` does the same for `AKAN_NPM_REGISTRY`. Export them in the shell instead, or run under `bun --no-env-file`, where they are always read. `SSH_TUNNEL_USERNAME`, `SSH_TUNNEL_PASSWORD` and `SSH_TUNNEL_PORT` are still read from a dotenv file, and `--registry` is unaffected.
- **`akan download-env` copies only env and secret files.** The archive is unpacked into a temporary folder under `local/`. Only `apps/<app>/env/env.{client,server}.*.ts`, `libs/<lib>/env/env.{client,server}.*.ts` and the files an app's `secrets` patterns name are copied into the workspace. Every other entry, links included, is left out and listed in a warning.
- **The local registry listens on loopback.** `akan start-registry` now publishes Verdaccio's port as `127.0.0.1:<port>`, taking the port from `--registry`. A registry URL with an IP address (`--registry http://0.0.0.0:4873`) binds to that address instead. A running `akan-verdaccio` container that already listens on every interface gets a warning naming the command that recreates it.
- **The local registry takes anonymous publishes for the akan packages only.** The bundled `verdaccio.yaml` still lets anyone publish the Akan.js packages. Every other name, the ones proxied from npm, now needs a signed-in user, and sign-up stays off, so a local publish cannot stand in for an npm package. Give those entries `publish: $all` again to restore anonymous publishing.
- **Subspace names are plain folder names.** A subspace `name` takes letters, digits, `.`, `_` and `-`, and starts with a letter or digit. Any other name is refused when the config is read and when the clone is set up.
- **A Dockerfile built for the `local` environment stops `docker build`.** The generated Dockerfile of an image built with `AKAN_PUBLIC_ENV=local` fails right after its `FROM` line unless `--build-arg AKAN_ALLOW_LOCAL_IMAGE=1` is passed. Images built for any other environment, and a Dockerfile given verbatim in `akan.config.ts`, are unchanged.
- **The sample app's task writes need a signed-in user outside local and testing.** The workspace sample's `task.signal.ts` now guards its create, update and task actions with a new `LocalOrSignedIn` guard in `srvkit/guards.ts`. A guest still writes under `AKAN_PUBLIC_ENV` `local` or `testing`, so the sample's own tests keep running. Existing workspaces are unchanged.
- **`akan login` prefers the device-code answer.** When the cloud answers both ways, the CLI takes the session answered for its device code. A cloud that answers only for the sign-in URL's id still signs you in, and the CLI logs a warning.
- **`akan tunnel` keeps the dev-only routes local.** On opening a share, the CLI now says that anyone with the URL reaches the app without signing in. Through the share, devtools (`/_akan/devtools`, `/_akan/signal`, `/_akan/constant`, `/_akan/deps`, `/_akan/dictionary`), the HMR socket `/_akan/hmr`, `/_akan/app/*`, `/_akan/ops/*` and every `*.map` file answer 404, and an `x-akan-debug` header is dropped. Pages, their assets and the app's websocket pass through unchanged. `akan start --share` opens its shares through the same filter and prints the same notice. `akan tunnel --dev-routes` (`-d`) shares everything, as before.
- **The `no-unguarded-endpoint` lint and the agent guidelines describe the new defaults.** The lint says an endpoint without guards is refused with 403 and stops the boot outside local operation, and the guidelines and skills cover the ops channel's limits, snapshot encryption, the agent's write confirmation and request caps.
