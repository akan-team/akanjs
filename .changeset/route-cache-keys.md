The route caches key a page on the locale it resolved to, not on the `Accept-Language` it was asked in, and on its query sorted and without tracking parameters.

- The RSC and HTML result caches keyed every page on the request's raw `Accept-Language` as well as on the locale the locale proxy resolved from its path, so each set of browser languages kept its own copy of a page that renders the same for all of them. Only the resolved locale is in the key now, and visitors who ask for one locale's page in different languages share its entry. A page that reads the header with `headers()` is still rendered for each request and never stored.
- The key took the query exactly as requested, so `?b=2&a=1` and `?a=1&b=2`, or a link carrying `utm_source` or `gclid`, each rendered and stored their own copy. The key now takes the query sorted by name, as the URL standard parses it (a repeated name keeps its values in order), without the tracking parameters in `AKAN_ROUTE_CACHE_TRACKING_PARAMS`: by default `utm_*`, `gclid`, `gclsrc`, `dclid`, `gbraid`, `wbraid`, `fbclid`, `msclkid`, `twclid`, `ttclid`, `li_fat_id`, `igshid`, `yclid`, `mc_cid`, `mc_eid`, `_ga` and `_gl`. Set it to comma-separated names (a trailing `*` matches a prefix, `default` adds the built-in list) or to `off`.
- A page shares an entry across queries only when every level of its route declares what it reads with `.search()`. A page or layout with `.config({ canonicalQuery: false })`, one that declares a tracking parameter, and a legacy default-function page keep one entry per query as requested. A page keyed on the sorted query is rendered with that URL, whether the cache stores it or not: its `.search()` values are the request's, while a guard's `request.path`, `usePathCtx().location` and the router state carry the sorted query until the first client navigation, and `usePageLocation()` carries it until the URL's query moves, so the browser hydrates the query the server rendered. `window.location` keeps every parameter.
- Each process now counts its route cache lookups: the RSC cache in the render worker and the HTML cache in the web server, as hits and misses by whether the route's key took the query as requested or sorted and without tracking parameters, and as bypasses by why the request skipped the cache (an environment opt-out, the dev default, a zero TTL, an excluded path, a request that is not public, a dev registry or no matching route). The RSC count covers full-page lookups, not partial-commit patches.

**Upgrading.** Nothing changes for a page that reads `Accept-Language` with `headers()`. One that reads it through `untrackedHeaders()` or `headers({ trackDynamic: false })`, which skip the tracking that keeps a render out of the caches, now gets another language's stored copy: read it with `headers()` instead. A `page()` or `layout()` whose server render reads the query outside `.search()`, or reads a tracking parameter it does not declare, through `untrackedRequest()` for instance, now gets another query's stored copy: declare the parameter with `.search()` or set `.config({ canonicalQuery: false })` on it.

The sorted URL is what such a page renders with in every mode, not only when it is stored: in dev, with `AKAN_RSC_RESULT_CACHE=0` or `AKAN_HTML_RESULT_CACHE=0`, and for a request with cookies that skips the cache. Where a page needs the query as it was asked:

- A guard's `request.path` no longer carries tracking parameters or the order they came in, so a redirect such as ``/login?next=${request.path}`` drops `utm_*` on the way: declare each parameter it must pass on with `.search()`, which keys the route on its query as requested, or set `.config({ canonicalQuery: false })` on the route.
- On the client, `usePathCtx().location` and the router state keep the sorted query without tracking parameters until the first navigation, and `usePageLocation()` until the URL's query moves: declare the parameter with `.search()` or set `canonicalQuery: false` on the route, or read `window.location` in an effect, after hydration.
