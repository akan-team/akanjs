A browser's access token now lives one hour instead of seven days, and `@libs/shared` gains `session.cookieOnly`: with it on, a server-rendered web app holds its session in HttpOnly cookies alone.

- **One hour, one source.** `accessTokenSeconds` in `@libs/util/common` is the lifetime `signAccessToken` uses by default. The refresh token still lives 30 days, the session cookies keep their 30 day `Max-Age`, and an OAuth client's token still follows `oauth.accessTokenSeconds`.
- **Seven days still, for a caller that keeps its tokens itself.** A native shell, a client-rendered app on another origin, a server (`fetch.clone`) and a test keep the seven day token in this release (`WebSession.cookielessAccessTokenSeconds`), with `session.cookieOnly` on or off. The request has to ask for body tokens (the header below, or an allowlisted origin other than the server's own), carry no session cookie, and not come from a page on the server's own host. A page on the server's own host is a request whose `Origin` is that host, with or without its default port and whatever the letter case, or one the browser marks `Sec-Fetch-Site: same-origin`, as it does a same-origin `GET` that carries no `Origin`. A page on a sibling subdomain (`same-site`) is another origin's app and keeps seven days, and so does a caller that names no origin at all. Every other caller gets one hour: a server-rendered page, any request that carries a session cookie, a page load's renewal, a call sent over the websocket, and a hand-written call that does not ask. `AccountMiddleware` decides per request and the `@libs/shared` user and admin services sign with `WebSession.accessTokenExpiresAt()`.
- **Renewal.** A page refreshes two minutes before the token expires. It rechecks the expiry when its tab becomes visible, when the window takes focus, when the network comes back and once a minute, so a device that slept past the expiry renews as soon as it wakes. The page counts the token's lifetime on the server's clock, not the device's: each refresh answer measures how far the device clock is off (the token's `iat` against the moment the refresh was asked), the measurement is kept in client storage for the next page load, and a token found at load that disagrees with it is refreshed once to measure again. A device clock that is fast by less than half the token's lifetime is taken as it reads, which only renews early. An answered refresh is not asked again within a minute. New: `@libs/shared` registers `option.setSessionRefresh`, so a page load or RSC navigation that arrives with an expired access token is renewed from the request's refresh cookies before it renders. A user and an admin identity held together each come back on their own refresh cookie. An app's own `setSessionRefresh` wins over the lib's, and `setSessionRefresh(null)` turns it off.
- **Renewal that holds together.** A browser signed in as user and admin sends its two refreshes one after the other, in one tab and across tabs, so both identities survive a tab that wakes after the expiry. When one of the two sessions has ended, only that identity goes: `refreshAdminJwt` answers a session held in cookies whose admin session ended with the user identity alone, signed to the expiry it already had, and expires the admin refresh cookie; with no live user identity it ends the session as before. `refreshJwt` refuses an ended user session without changing a cookie, so the admin stays signed in. `Auth.TokenRefresh` redraws the page when a refresh leaves the session without its own identity, before the old token's expiry too. A refresh that failed is tried again after three seconds, then after 30 seconds doubling up to ten minutes, and at once when the window takes focus or the network comes back. `refreshAdminJwt` answers a refresh token presented twice within ten seconds, as `refreshJwt` does. A call whose `Authorization` token is this app's own and past its expiry is read by its session cookie instead, so a tab that has not refreshed yet follows the session a page load or another tab renewed; a token that is malformed, signed with another key, minted for another app or environment, or revoked is still answered as signed out.
- **`session.cookieOnly`** (`env.server.*`, off by default). Sign-in, SSO completion and refresh (`signinWithPassword`, `signinWithPhoneCode`, `signinWithSignToken`, `exchangeSsoCode`, `activateUser`, `activateUserWithAgreePolicies`, `refreshJwt`, `signinAdmin`, `refreshAdminJwt` and the other answers built by `makeAccessTokenResponse`) answer a server-rendered page with the session and refresh cookies and a body of `{ jwt: "", expiresAt }`: no token and no `refreshToken` field. The page's calls, file uploads, agent stream and websocket authenticate by cookie, and the page sends no `Authorization` header. One endpoint still answers an admin's page with tokens in the body: `getAccessTokenByAdmin` hands the admin another user's session, which a cookie could not carry without replacing the admin's own.
- **Who still gets tokens in the body.** A caller that holds no session cookie and asks for them with the request header `x-akan-session-tokens: body`. The framework's `fetch` sends it to its own server from a native shell, a client-rendered app, a server (`fetch.clone`) and a test, and never from a server-rendered page. A page on an allowlisted origin other than the server's own counts as asking, so a native app released before this version keeps working. Such an answer sets no session cookie.
- **Framework.** `sessionTokenContract` in `akanjs/common` names the header. `setAuth()` with no token beside a session the server holds stops `fetch` from sending one and reconnects the socket so its handshake carries the cookie. `WsClient.connect({ fresh: true })` replaces an open socket. `CrossSiteGuard.isFromOwnHost(req, url)` in `akanjs/signal` answers whether a request's `Origin` is the serving host. `@libs/shared` adds `ServerClock` (`common`) and `SessionClock` (`webkit`), which `refreshSession` and `Auth.TokenRefresh` read a token's expiry through.

**Upgrading.**

1. For everyone: a browser's access token expires after an hour. Nothing changes in an app that mounts `Auth.User` / `Auth.Admin` (they mount `Auth.TokenRefresh`) and uses the `@libs/shared` sign-in endpoints. In an app that mounts neither, an open tab's calls and socket go anonymous an hour after sign-in until the next navigation or reload, which renews the session: mount them, or call `refreshSession` from your own code. A native app, a client-rendered app on another origin and a script that signs in through the framework's `fetch` keep seven days. A hand-written HTTP call that keeps its own token and does not send `x-akan-session-tokens: body` gets one hour, and must refresh with `refreshJwt` / `refreshAdminJwt` or sign in again. `getAccessTokenByAdmin` signs for the kind of caller the admin is: one hour for a page on the server's own host or a caller that holds a session cookie, seven days for an admin app on another origin that keeps its tokens itself.
2. `RevokedSessions.accessTokenDays` is gone. `RevokedSessions.deniedSeconds` is how long a revoked session's tokens stay refused, and stays seven days.
3. A deployment that answers CORS preflights from its own edge list adds `x-akan-session-tokens` to the allowed request headers: a native shell and a client-rendered app on another origin send it with every call. The chart's `ingress.cors.enabled: true` list names it now, and the app's own CORS answer already allows every header a preflight asks for.
4. Your own endpoint that answers with `makeAccessTokenResponse` or `makeAdminAccessTokenResponse` passes the request, `makeAccessTokenResponse(token, { req })` (`.with(Req)`). With `session.cookieOnly` on, an answer that names no request never carries tokens in its body.
5. To turn the option on, set `session: { cookieOnly: true }` in `env/env.server.<env>.ts`. Client code that reads `jwt` or `refreshToken` from a sign-in or refresh answer in a server-rendered page gets an empty string and no field: hand the answer to `setAuth` as the `@libs/shared` stores do, and read the signed-in account with `getAccount()` / `getSelf()`.
6. Do not turn it on yet if your web pages are served as the client-rendered view on the server's own host (`?csr=true`, `/__csr`) in a browser that also holds the session cookie, if a client of yours on another origin that is not in the allowlist reads body tokens with a hand-written HTTP call, or if page code needs the token itself, for example to put it in a URL or hand it to another service. Tabs still running the code from before the deploy keep their session by cookie, but at their first refresh they lose their live subscriptions and stop scheduling refreshes, so their calls go anonymous about an hour later until a navigation or reload.
7. In 3.5.0 `session.cookieOnly` is on unless you set it to `false`.
