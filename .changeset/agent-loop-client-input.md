`agentService.loop` bounds what a page sends into a run through `clientTools` and `answer`, and what another server sends into one through `remotes`.

- **Tool definitions.** A run takes at most 128 client tools and 200,000 characters of their definitions, about twenty times what a screen lends today, nested at most 64 levels deep. Past any of the three, the run ends with an `error` event whose `error` is `agent.error.clientToolsRefused` (status 413), with `data.limit` `"tools"`, `"chars"` or `"depth"`, `data.max` and `data.sent`.
- **Writes.** A client tool counts as a write whatever `readOnly` it was sent with: `approve` sees `tool.readOnly: false`, and a run with no `approve` refuses it once tainted. Which client tools may run after a read is the app's to say, in `approve`, by name.
- **Answers.** Every part of an `answer` is bounded where it enters the transcript. Its `result`, its `error`, its `changes` taken as one value and a text attachment are each clipped at 20,000 characters, as a tool's result is. Its `code` is kept only when it is a failure code: a dictionary key or a camelCase token. Of its `attachments` the first four that carry `data` or `text` are kept, never a `url`, each with a `name` and a `mimeType` of at most 255 characters and under the 4 MiB ceiling a tool's file has.
- **Size caps.** A run that lists `clientTools` meets the relay's default size caps (`AgentRelayPolicy.defaultLimits`) on each of its turns, and ends with `agent.error.requestRefused` past them. `AgentTurnContext.loop` gains `client: true` on those turns, so a policy of the app's own can tell them apart. A run with neither `clientTools` nor `remotes` still skips the caps. A file a tool returned now counts under `attachmentChars` like a user's attachment, on relayed turns too, where it used to count under `chars`: two pictures of five million characters each no longer end a run. A file whose `data` or `text` is not a string is sized by its JSON, and a turn whose `toolResults` or `attachments` is not a list of objects is refused with `agent.error.requestRefused`.
- **Remotes.** A run that names `remotes` meets the same default size caps on each of its turns, which carry `loop.remote: true`. It keeps at most four remotes open, as each open listing of up to 120,000 characters rides every later round: the open of a fifth is answered with an error and that server is not contacted. A resume leaves closed a remote that a stored call found disconnected, as the run that stored that call did, so it does not count toward the four. A `view` on a `toolResult` event carries no `href` or `resourceUri` longer than 2,048 characters. Of what a remote's `call` returns, the run keeps only `result`, `error`, `code`, `changes` and `attachments`, each bounded as the parts of an `answer` are: `result`, `error` and `changes` as one value clipped at 20,000 characters, `code` only when it is a failure code, and the first four attachments that carry `data` or `text`, never a `url`. Any other field is dropped, where it used to be stored as sent.

**Upgrading.** An app built on a 3.2.0 release candidate changes nothing unless it relied on one of these:

- A page that marked a tool `readOnly: true` in what it sent, to keep it callable after a read in a run with no `approve`: pass `approve` and allow that tool by name.
- A request policy set with `option.setAgentRequestPolicy` that returns loop rounds untouched keeps doing so; to cap the rounds of a run with client tools or remotes, return `AgentRelayPolicy.capped(request)` when `context.loop?.client` or `context.loop?.remote` is set.
- An answer that carried a file by `url`: send its bytes as `data`, or have an endpoint tool return it.
